# V1.5 Velocity-Based Tier Pricing — Supliful-inspired dynamic fees

> **STATUS: SPEC ONLY — NOTHING SHIPPED.** V1.5 Track C extension (On-Demand). Locked 2026-06-03 after Supliful price-tier model review.

> The single most important pricing-model upgrade in V1.5. Adds a per-SKU velocity tier on top of the locked subscription tier model. Velocity rewards proven product-market-fit; subscription tier remains the floor.

## 🔀 Dual-system update — 2026-06-04

**This doc covers ON-DEMAND velocity tiers only.** Bulk orders use a separate per-order quantity tier system documented in `_V1.5_BULK_PRICING.md`. The two systems are economically distinct:

| Mode | What drives cost down? | Tier mechanic |
|---|---|---|
| **On-demand** | Velocity over time (more orders/mo = more orchestration efficiency) | Per-SKU 30-day rolling units (this doc) |
| **Bulk** | Quantity per order (bigger run = lower per-unit setup amortization) | Per-order quantity tier (`_V1.5_BULK_PRICING.md`) |

**Cross-pollination preserved.** Bulk units on a SKU still accrue toward that SKU's on-demand velocity tier. This is the key mechanism — a creator's bulk seed run unlocks better on-demand fees forever. See "Cross-pollination rule" below.

**What changed in this doc:** the original velocity-tier table at the top covers ON-DEMAND fee % only. Bulk orders no longer use velocity-tier fee discount — bulk's pricing leverage moves to the wholesale tier ladder + flat platform fee (15%/10%/7%) per the new bulk doc. The "lower-of" logic still applies at quote time: bulk quote vs on-demand velocity tier quote, creator gets the better price.

## The economic principle

Current locked on-demand model (from `on-demand-pricing-economics.md`):

- Maker: 15% platform fee per fulfilled on-demand order
- Builder: 10% (with $49/mo subscription)
- Agency: 7% (with $199/mo subscription)

Currently velocity-blind. A Builder doing 5 orders/mo on one SKU pays the same fee % as a Builder doing 500 orders/mo on that same SKU. That's leaving money on the table for everyone — creators with proven SKUs should pay less; iLaunchify should reward stickiness.

**The Supliful-inspired upgrade:** on top of the subscription-tier base rate, layer a per-SKU velocity discount based on rolling 30-day fulfilled-unit volume. The more a creator sells of a specific Product, the cheaper each subsequent unit gets — across both on-demand AND bulk.

## Locked velocity tier table (V1.5 seed values, admin-configurable)

Stored in `VelocityTierThreshold` model — admin can tune at any time without code release. V1.5 seed:

| Velocity tier | 30-day SKU volume | Maker | Builder | Agency |
|---|---|---|---|---|
| Tier 1 | 0-50 units | 15.0% | 10.0% | 7.0% |
| Tier 2 | 51-200 units | 13.0% | 8.5% | 6.0% |
| Tier 3 | 201-500 units | 11.0% | 7.0% | 5.0% |
| Tier 4 | 501-1000 units | 9.0% | 6.0% | 4.0% |
| Tier 5 | 1000+ units | 7.0% | 5.0% | 3.0% |

Five tiers initially. Admin can add tier 6/7 if Agency creators consistently exceed 1000 units/SKU/month — defer until real distribution signal exists.

## Cross-pollination rule (locked)

Bulk volume on the same `ProductId` counts toward that SKU's 30-day on-demand velocity tier. A creator who:

1. Runs a 500-unit bulk seed of their honey SKU in week 1 → tier jumps to Tier 3 immediately
2. Then sells 180 jars on Shopify on-demand over next 30 days → on-demand sells at Tier 3 fee % (Builder: 7% instead of 10%)
3. By end of month 30-day window: 500 bulk + 180 on-demand = 680 units → Tier 4 next billing cycle

This makes the locked `FulfillmentMode.BOTH` mode the economically obvious choice for creators serious about growing. Bulk seeds aren't sunk-cost; they're a velocity-tier unlock.

## Samples rule (locked, NEW)

Adds to existing sample-order rules in `on-demand-pricing-economics.md` §"Sample order pricing":

| Existing rule | NEW velocity-tier rule |
|---|---|
| Sample = at-cost (partner wholesale + shipping) | Sample charged at partner's Tier 1 base wholesale, never volume-discounted |
| 0% iLaunchify platform fee on samples | iLaunchify platform fee still 0% (unchanged) |
| Cap: ~10 samples per product per month per creator | Sample units do NOT accrue toward 30-day velocity tier — prevents gaming the system by claiming N "samples" to boost tier |

Audit-logged as `ON_DEMAND_SAMPLE_ORDER` (existing event). Velocity-tier calc explicitly excludes rows with this audit type.

## "Lower-of" pricing logic (locked)

Borrowed from Supliful. If a creator's current bulk quote for SKU X comes out at a HIGHER per-unit price than their on-demand Tier-N quote for the same SKU, iLaunchify charges the on-demand Tier-N price instead.

Implementation: at price-quote time, compute both rates, take min. Surface the comparison transparently in OrderSummary so the creator sees they got the better price.

Why: prevents creator regret on bulk commitments. A creator who books a 500-unit bulk and then immediately graduates to Tier 4 shouldn't pay Tier 3 rates on the run they pre-committed to.

## Schema additions

```prisma
model ProductFulfillmentVelocity {
  // Per (creator × ProductTemplate) rolling tier state
  id                      String   @id @default(uuid())
  creatorUserId           String
  productTemplateId       String   // tracks at template level, not at instance level
  
  // 30-day rolling windows recomputed by nightly background job
  unitsLast30dOnDemand    Int      @default(0)
  unitsLast30dBulk        Int      @default(0)
  unitsLast30dSamples     Int      @default(0)   // tracked but NOT counted toward tier
  unitsLast30dTotal       Int      @default(0)   // = onDemand + bulk (samples excluded)
  
  currentVelocityTier     Int      @default(1)
  
  recomputedAt            DateTime
  
  @@unique([creatorUserId, productTemplateId])
  @@index([recomputedAt])
}

model VelocityTierThreshold {
  // Admin-tuneable thresholds
  tier                Int       @id
  minUnits            Int       // inclusive
  maxUnits            Int?      // null = unlimited (top tier)
  
  // Effective platform fee % per subscription tier at this velocity
  makerFeePct         Decimal   @db.Decimal(5, 2)
  builderFeePct       Decimal   @db.Decimal(5, 2)
  agencyFeePct        Decimal   @db.Decimal(5, 2)
  
  displayName         String    // "Tier 3 — 201-500 units"
  
  updatedAt           DateTime  @updatedAt
}

// Audit log of every tier recompute / change — surface in admin
model VelocityTierAudit {
  id                  String   @id @default(uuid())
  creatorUserId       String
  productTemplateId   String
  
  previousTier        Int
  newTier             Int
  
  unitsAtRecompute    Int
  triggeredBy         VelocityTriggerType   // NIGHTLY_CRON | ORDER_PLACED | BULK_PLACED | ADMIN_RECOMPUTE
  
  createdAt           DateTime @default(now())
  
  @@index([creatorUserId, productTemplateId])
  @@index([createdAt])
}

enum VelocityTriggerType {
  NIGHTLY_CRON
  ORDER_PLACED          // recompute on every fulfilled order
  BULK_PLACED           // recompute on bulk order placement
  ADMIN_RECOMPUTE       // manual admin trigger
}
```

## Background recompute job

Nightly cron (low-traffic hour, configurable):

```typescript
async function recomputeVelocityTiers() {
  // Walk all distinct (creator, productTemplate) pairs with activity in last 35 days
  // (use 35-day window to catch edge cases at boundary)
  
  const pairs = await prisma.$queryRaw`
    SELECT DISTINCT "creatorUserId", "productTemplateId"
    FROM "Order"
    WHERE "createdAt" > NOW() - INTERVAL '35 days'
      AND "status" IN ('FULFILLED', 'SHIPPED', 'DELIVERED')
  `;
  
  for (const { creatorUserId, productTemplateId } of pairs) {
    const windows = await computeWindows(creatorUserId, productTemplateId);
    const tier = lookupTier(windows.unitsLast30dTotal);
    
    await upsertVelocity({ creatorUserId, productTemplateId, ...windows, tier });
    
    if (tier !== previousTier) {
      await writeAuditLog({ ...changeDelta, triggeredBy: 'NIGHTLY_CRON' });
      await notifyCreatorOfTierChange(creatorUserId, productTemplateId, previousTier, tier);
    }
  }
}
```

ALSO recompute on every fulfilled-order or bulk-placed event for real-time accuracy on edge cases — debounced per (creator, product) to once per 5 min to avoid hot loops.

Notification on tier change: short Resend email + in-app notification banner. "Your honey SKU just hit Tier 3 — Builder fee on this SKU drops from 10% to 7%."

## Marketplace product detail page — dynamic calculator (locked)

Pavel asked for this explicitly: the product detail page must show a live price calculator with full breakdown, not just a static price.

**Two display modes:**

### Guest mode (not signed in)

Shows the calculator with default assumptions:
- Quantity slider (default = 100 or MOQ if higher)
- Retail price input (creator-controlled, defaults to suggested)
- Subscription tier dropdown defaults to "Maker (free)"
- Velocity tier defaults to Tier 1
- Each line shows live numbers
- CTA: "Sign in to see your actual tier rate"

### Signed-in mode

Pulls actual values from the creator's account:
- Their `CreatorProfile.subscriptionTier`
- Their `ProductFulfillmentVelocity.currentVelocityTier` for this Product (Tier 1 if no history)
- Their default warehouse + shipping rate
- Surfaces "You'd be at Tier N after 50 more units" line as upgrade nudge

## Marketplace product detail dynamic calc — V1 vs V1.5 split

**V1** (per the existing Track B B1 task — wire `ProductTemplatePricingTier` real formula):

- Quantity / retail input
- Real manufacturer + shipping + platform fee at subscription tier base rate
- Signed-in / guest split
- No velocity tier line, no "your path" widget

**V1.5** (this doc):
- Velocity tier line added to breakdown

This lets V1 ship the transparent calculator on time (closes biggest creator-trust gap in the marketplace audit) without blocking on velocity model. V1.5 layers velocity in cleanly when it ships.

## Integration with existing admin/tiers shell

The R15.c-shipped `/admin/tiers` shell already has Creators / Partners / Plans tabs. Add a fourth tab "Velocity" so all tier-related controls live in one place. The Velocity tab structure:

```
/admin/tiers
  ├── Creators    (R15.d shipped — per-creator subscription tier + fee override)
  ├── Partners    (R15.d shipped — per-partner tier + fee override)
  ├── Plans       (R15.e shipped — PlanFeature + FeeRule inline editor)
  └── Velocity    (NEW — VelocityTierThreshold inline editor + recompute action)
```

The Velocity tab uses the existing cream-header v2 admin surface pattern + the inline-cell editor pattern from R15.e Plans & Fees. Matrix shape:

```

─────────────────────────────────────────────────────────────────────────────
```

## Source — Supliful price-tier model

This V1.5 upgrade is inspired by Supliful's `Understanding Supliful's product price tiers` mechanic. We borrowed three principles (per-SKU velocity, cross-pollination, lower-of) and rejected three others (no custom formulation, single-vendor fulfillment, opaque pricing).
